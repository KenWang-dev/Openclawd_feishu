> **文档性质**：管理层决策参考
> **版本**：v1.0
> **日期**：2026-05-06
> **机密等级**：内部

---

## 一、执行摘要

### 我们要解决什么问题

手机 ODM 厂商的售后维修部门面临三个核心痛点：

| 痛点 | 现状 | 影响 |
|------|------|------|
| **经验断层** | 老师傅离职 = 知识归零 | 新人培养周期 6-12 个月，维修良率波动大 |
| **维修效率低** | 简单故障也要找资深工程师确认 | 单台平均维修时长偏长，旺季产能瓶颈 |
| **质量无法追溯** | 维修记录散落在纸质单据和个人笔记中 | 无法做根因分析，同一问题反复出现 |

### 核心结论

**推荐方案：以 LLM Wiki 知识沉淀体系为底座 + 轻量级 AI 诊断引擎 + 维修全流程管理**

不是一个开源项目的简单移植，而是吸收四个参考项目的核心方法论，针对手机 ODM 场景重新设计。

## 二、方案对比：为什么选这个

### 2.1 四个参考项目评估

| 维度 | Wrench Board | ARIA | MaestrIA | LLM Wiki |
|------|-------------|------|----------|----------|
| **解决什么** | 电路板故障诊断 | 工厂设备预测性维护 | 房屋维修拍照诊断 | 个人知识管理 |
| **核心能力** | 原理图解析 + 逐步标注 | 多 agent 协作 + 实时数据 | 拍照识别 + 报价 + 派单 | 结构化知识沉淀 + 双向链接 |
| **与手机维修的匹配度** | ⭐⭐⭐⭐ 原理图诊断直接可用 | ⭐⭐⭐⭐ 多 agent 架构可复用 | ⭐⭐⭐ 流程层可参考 | ⭐⭐⭐⭐⭐ 知识沉淀是刚需 |
| **代码可直接复用程度** | 低（通用电路板，非手机） | 低（工业设备场景） | 低（房屋维修场景） | 中（方法论可复用，需适配） |
| **方法论价值** | 极高 | 极高 | 中等 | 极高 |

**关键判断：四个项目都没有一个是"拿来就能用"的。但方法论价值极高。**

### 2.2 为什么不直接用某一个

| 如果只用… | 会缺什么 |
|-----------|---------|
| 只用 Wrench Board | 没有知识沉淀，每次诊断从零开始；不支持手机特有的多层 PCB 和 BGA 元件 |
| 只用 ARIA | 架构过重，手机维修不需要预测性维护的实时性；没有维修知识库 |
| 只用 MaestrIA | 只是拍照 + 派单，没有真正的诊断能力；没有经验积累 |
| 只用 LLM Wiki | 只是知识库，没有诊断推理能力；不支持实时维修指导 |

### 2.3 我们的方案：兼收并蓄

**从每个项目吸收最核心的方法论，重新组合为手机维修场景量身定制的方案：**

## 三、技术栈设计

### 3.1 分层架构

```
┌─────────────────────────────────────────────┐
│  前端层：维修技师工作台                        │
│  Web App (响应式) + 移动端 (未来)              │
├─────────────────────────────────────────────┤
│  API 网关层                                  │
│  FastAPI / Go                                │
├─────────────────────────────────────────────┤
│  业务逻辑层                                  │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐    │
│  │ 流程引擎  │ │ 诊断引擎  │ │ 知识引擎  │    │
│  └──────────┘ └──────────┘ └──────────┘    │
├─────────────────────────────────────────────┤
│  AI 编排层                                  │
│  LLM 调用 · Agent 协作 · Prompt 管理         │
├─────────────────────────────────────────────┤
│  数据层                                     │
│  Markdown 知识库 · 向量数据库 · 关系型数据库   │
├─────────────────────────────────────────────┤
│  基础设施层                                  │
│  本地服务器 / 私有云 (数据不出厂)              │
└─────────────────────────────────────────────┘
```

### 3.2 技术选型明细

| 层级 | 推荐技术 | 选择理由 | 备选 |
|------|---------|---------|------|
| **知识库格式** | Markdown 文件 + Git 版本管理 | Karpathy 方法论核心；LLM 原生可读；可 diff 可追溯；Obsidian 兼容 | Notion API / 飞书知识库 |
| **知识图谱可视化** | D3.js / ECharts | 轻量、可定制、离线运行 | Neo4j (过重) |
| **向量检索** | ChromaDB / Milvus | 本地部署、轻量、支持中文 | Qdrant / Weaviate |
| **LLM 推理** | 本地部署 Qwen2.5 / DeepSeek-V3 | 数据不出厂是硬要求；中文能力强 | Claude API / GPT-4o (需评估数据安全) |
| **Agent 编排** | LangChain / 自研轻量框架 | 成熟度高；或参考 ARIA 架构自研更轻量 | CrewAI / AutoGen |
| **后端框架** | FastAPI (Python) | AI 生态最好；开发速度快 | Go (性能更好但 AI 库少) |
| **前端** | React + Ant Design | 组件丰富；维修技师使用门槛低 | Vue3 |
| **图片处理** | OpenCV + YOLO | 主板元件识别；X 光/热成像预处理 | — |
| **数据库** | PostgreSQL | 关系型数据（工单、用户、统计） | MySQL |
| **部署** | Docker Compose / K8s | 容器化部署，便于扩展 | 物理机直接部署 |

### 3.3 数据安全策略

| 措施 | 说明 |
|------|------|
| **LLM 本地部署** | 维修数据涉及客户手机信息，禁止外传 |
| **知识库本地 Git** | 所有维修案例和 SOP 存储在本地服务器 |
| **图片脱敏** | 上传照片自动模糊客户个人信息（IMEI、姓名等） |
| **权限分级** | 徒工 / 初级技师 / 高级技师 / 工程师，看到的信息不同 |
| **审计日志** | 所有查询和诊断记录可追溯 |

### 4.1 团队配置

```
项目组
├── 项目经理 × 1（兼产品Owner）
│   负责需求管理、优先级、进度把控
│
├── AI 工程师 × 1-2
│   负责 LLM 集成、Agent 编排、Prompt 工程
│
├── 后端开发 × 1-2
│   负责 API、数据库、业务逻辑
│
├── 前端开发 × 1
│   负责维修工作台界面
│
├── 知识工程师 × 1（关键角色）
│   负责维修知识结构化、故障树设计、SOP 整理
│   ★ 建议从资深维修工程师中培养
│
├── 领域专家（兼职/顾问）× 2-3

    负责维修方案准确性验证
```

### 4.3 关键角色说明

**知识工程师（最重要但不被重视的角色）**

这个人是整个项目的成败关键。他的工作不是写代码，而是：

1. 把老师傅脑子里的经验变成结构化文档
2. 设计故障分类体系（故障树）
3. 制定维修 SOP 的标准格式
4. 审核AI生成的诊断方案是否合理
5. 建立知识库的质量标准（置信度标注）

**为什么不是"让AI自己学"**：维修经验中有大量隐性知识（"摸一下这个芯片发烫就是它坏了"），这类知识无法从文本中自动提取，必须有人工结构化。

## 五、实施路线图

### 5.1 三阶段实施

```
Phase 1: 知识基建（第 1-2 月）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━
目标：建好知识底座，让系统能"记住"经验

  Week 1-2: 知识体系设计
    □ 确定首批覆盖的机型（建议选 3-5 个主力机型）
    □ 设计故障分类体系（按子系统分：电源/射频/显示/音频/...）
    □ 制定维修记录的标准格式
    □ 搭建 LLM Wiki 基础设施（目录结构 + 模板 + Git）

  Week 3-6: 知识录入
    □ 录入 3-5 个机型的原理图、BOM、维修手册
    □ 整理 Top 50 常见故障的维修 SOP
    □ 录入最近 6 个月的维修记录（去敏后）
    □ 建立元器件知识库（常用 IC 的参数和损坏模式）

  Week 7-8: 验证
    □ 选 10 个维修技师做内测
    □ 场景：给定故障描述，系统返回匹配的历史案例
    □ 目标：Top 50 故障的匹配准确率 > 80%

  交付物：
  ✅ 知识库（3-5 个机型，50+ 故障案例）
  ✅ 基础查询功能（故障描述 → 推荐方案）
  ✅ 知识管理体系文档


Phase 2: AI 诊断（第 3-5 月）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━
目标：让系统能"诊断"故障，而不只是"检索"案例

  Week 9-10: 诊断引擎 v1
    □ 实现 Agent 1（信息采集）：结构化故障描述 + 测量数据输入
    □ 实现 Agent 2（知识检索）：从 Wiki 匹配 + 向量检索相似案例
    □ 实现 Agent 3（方案生成）：综合输出分步维修指引

  Week 11-14: 原理图分析
    □ 接入手机主板原理图（Gerber / PDF）
    □ 实现原理图上的故障路径标注（参考 Wrench Board）
    □ 支持常见测量点自动标注（电压测试点、关键信号路径）

  Week 15-16: 多模态输入
    □ 接入主板照片（普通拍照 + 显微镜拍照）
    □ 实现元件级识别（烧毁痕迹、虚焊、腐蚀等）
    □ 接入万用表测量数据输入

  Week 17-20: 测试优化
    □ 扩大内测范围到 50 个维修技师
    □ 收集诊断准确率数据
    □ 迭代优化 Prompt 和知识库
    □ 目标：常见故障诊断准确率 > 70%

  交付物：
  ✅ AI 诊断引擎（故障描述 + 测量数据 → 分步方案）
  ✅ 原理图标注功能
  ✅ 图片辅助诊断
  ✅ 诊断准确率报告


Phase 3: 流程打通（第 6-8 月）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━
目标：让系统融入维修全流程，形成闭环

  Week 21-24: 维修工作台
    □ 开发 Web 工作台（接单 → 诊断 → 维修 → 验证 → 归档）
    □ 集成现有 MES/ERP 系统（工单号、物料、人员）
    □ 实现自动归档：维修结果自动写入知识库

  Week 25-28: 智能化升级
    □ 实现维修成本评估（修 vs 换板，经济性建议）
    □ 实现预测性分析（某机型某元件的故障趋势）
    □ 实现新人培训模式（交互式故障诊断练习，参考 MedKit）
    □ 实现质检反馈闭环（返修数据回流优化诊断）

  Week 29-32: 全面上线
    □ 全部门推广
    □ 建立持续运营机制（知识库日常维护、模型迭代）
    □ 建立效果度量体系

  交付物：
  ✅ 完整维修工作台
  ✅ ERP/MES 集成
  ✅ 知识闭环（维修 → 归档 → 优化）
  ✅ 效果度量仪表板
```

## 八、关键成功因素

### 8.1 最重要的一件事

**不是技术，是知识工程师。**

技术方案可以换，但如果没有一个能把老师傅的经验结构化的人，整个项目就是空中楼阁。这个角色最好从内部资深维修工程师中培养——他既懂维修，又愿意学习知识管理的方法论。

### 8.2 不要犯的错误

| ❌ 错误 | ✅ 正确做法 |
|---------|-----------|
| 一上来就搞 AI 诊断 | 先把知识库建好，让"检索"先跑起来 |
| 让所有机型一起上 | 先选 3-5 个主力机型，做深做透 |
| 期望 AI 替代维修技师 | 定位是"辅助工具"，技师做最终决策 |
| 知识库交给 AI 自动构建 | 人工结构化 + AI 辅助，不能全自动 |
| 一次性全面上线 | 三阶段递进，每阶段独立产生价值 |

### 8.3 如何衡量成功

| 指标 | Phase 1 目标 | Phase 3 目标 |
|------|-------------|-------------|
| 知识库条目数 | 200+ | 1000+ |
| 维修技师日均使用次数 | 5 次 | 15 次 |
| 常见故障诊断准确率 | 80%（检索） | 85%（AI 诊断） |
| 新人独立上岗周期 | — | 缩短 30% |
| 返修率 | 基线记录 | 下降 15% |
| 单台平均维修时长 | 基线记录 | 缩短 20% |

## 九、后续扩展方向

系统跑起来之后，数据积累到一定量，可以自然延伸出以下能力：

### 9.1 短期（9-12 月）

- **新人培训模式**：参考 MedKit（黑客松金奖），做一个交互式故障诊断练习系统，新人可以在 AI 上犯错练手
- **跨机型模式发现**：用知识图谱分析"同一个电源芯片在三个不同机型上都容易坏"，反馈给研发部门改进设计
- **物料预警**：某元件故障率突增 → 自动预警供应链

### 9.2 中期（12-18 月）

- **供应商质量追踪**：把维修数据和BOM关联，量化不同供应商同一元件的故障率差异
- **远程维修支持**：海外工厂的维修技师通过系统获取总部专家的知识支持
- **客户服务集成**：维修记录自动生成客户沟通模板

### 9.3 长期（18+ 月）

- **预测性维护**：参考 ARIA，从维修数据中学习故障前兆，实现"坏了之前就知道要坏"
- **研发反馈闭环**：高频故障自动生成研发改进建议（DFM/DFR 反馈）
- **行业知识平台**：将知识体系标准化，成为公司的核心数字资产

## 十、总结

### 一句话说清楚

**用 Karpathy LLM Wiki 的方法把维修经验沉淀成结构化知识库，用 Wrench Board 的思路做 AI 诊断引擎，用 ARIA 的多 agent 架构做系统骨架，用 MaestrIA 的流程思维打通维修全流程。**

### 为什么是现在

1. **LLM 能力已经够用**——Qwen2.5 / DeepSeek-V3 中文推理能力足以处理维修诊断
2. **方法论已经验证**——Anthropic 黑客松证明"领域专家 + AI"可以做出生产级工具
3. **知识管理工具成熟**——Karpathy 的 LLM Wiki 方法论已经大规模验证
4. **竞争对手在行动**——领先厂商已经开始用 AI 做售后，不动的就会落后

### 给管理层的建议

> **不要把这个项目当成"IT 项目"，把它当成"知识资产建设项目"。**
>
> 技术会过时，但沉淀下来的维修知识库是公司的永久资产。就算三年后换了更好的 AI 模型，知识库依然可用。
>
> 建议从 Phase 1 启动，2 个月、投入 ~15 万，先验证知识库的价值。如果技师反馈积极，再投入 Phase 2 和 3。
