第五卷：综合实战

学习目标：通过 4 个完整实战项目，将前面学到的所有知识串联起来。读完本卷后，你已具备独立使用 Claude Code 完成真实项目的能力。

第27章：实战 1 —— 从零搭建全栈应用

27.1 项目概述

目标：用 Claude Code 从零搭建一个任务管理应用（TaskBoard），包含前后端和数据库。

技术栈： - 前端：React + TypeScript + Tailwind CSS - 后端：Node.js + Express + TypeScript - 数据库：SQLite（通过 Prisma ORM） - 测试：Vitest（前端）+ Jest（后端）

27.2 Step 1：项目初始化

mkdir taskboard && cd taskboard
git init
claude

给 Claude 的指令：

我要从零搭建一个任务管理应用 TaskBoard。

技术栈：
- 前端：React + TypeScript + Tailwind CSS（Vite）
- 后端：Node.js + Express + TypeScript
- 数据库：SQLite + Prisma ORM
- 测试：Vitest + Jest

项目结构要求：

taskboard/ ├── client/ # React 前端 │ ├── src/ │ │ ├── components/ │ │ ├── pages/ │ │ └── App.tsx │ └── package.json ├── server/ # Express 后端 │ ├── src/ │ │ ├── routes/ │ │ ├── middleware/ │ │ └── index.ts │ └── package.json ├── prisma/ │ └── schema.prisma ├── CLAUDE.md └── README.md


请先用 /init 生成 CLAUDE.md，然后用 Plan Mode 制定完整的实现计划。

27.3 Step 2：规划阶段（Plan Mode）

在 Plan Mode 中，制定分阶段实现计划：

阶段 1：基础架构（数据模型 + API 骨架）
阶段 2：核心 API 实现（CRUD）
阶段 3：前端框架搭建
阶段 4：前后端联调
阶段 5：测试
阶段 6：优化和文档

每个阶段列出：
- 需要创建的文件
- 主要功能
- 验证方式

27.4 Step 3：数据模型设计

Claude 在 Plan Mode 中输出的 Prisma schema：

// prisma/schema.prisma
datasource db {
  provider = "sqlite"
  url      = "file:./dev.db"
}

generator client {
  provider = "prisma-client-js"
}

model Task {
  id          String   @id @default(cuid())
  title       String
  description String?
  status      String   @default("todo") // todo | in-progress | done
  priority    String   @default("medium") // low | medium | high
  dueDate     DateTime?
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt
}

审查要点： - 字段类型是否合理 - 默认值是否正确 - 是否有遗漏字段（比如 userId）

27.5 Step 4：后端 API 实现

退出 Plan Mode（Ctrl+G），按计划执行阶段 1 和 2。

实现以下 API 端点：
- GET /api/tasks — 获取所有任务（支持筛选：status, priority）
- GET /api/tasks/:id — 获取单个任务
- POST /api/tasks — 创建任务
- PUT /api/tasks/:id — 更新任务
- DELETE /api/tasks/:id — 删除任务

每个端点要求：
- 输入验证（title 必填）
- 错误处理（404, 400, 500）
- 合适的 HTTP 状态码

实现后跑测试确认。

27.6 Step 5：前端实现

实现前端页面：

1. 任务列表页：显示所有任务，支持筛选和排序
2. 创建任务表单：标题、描述、优先级、截止日期
3. 任务卡片：显示状态、优先级，支持拖拽改状态

UI 要求：
- 响应式设计
- 加载状态和错误提示
- 空状态提示

实现后在浏览器中验证。

27.7 Step 6：测试

为后端 API 编写集成测试：
- 创建任务 → 验证返回
- 获取任务列表 → 验证筛选
- 更新任务状态 → 验证更新
- 删除任务 → 验证删除
- 边界情况：空标题、不存在的 ID

跑所有测试，确保通过。

27.8 Step 7：提交

将所有代码提交到 Git。
创建一个 PR，描述包括：实现了什么、技术栈、如何运行、如何测试。

第28章：实战 2 —— 大型代码库上手

28.1 项目概述

目标：克隆一个真实的开源项目，用 Claude Code 快速理解架构，并提交第一个 PR。

选择项目标准： - 有 5k+ star（说明有一定复杂度） - 有完善的 README 和文档 - 有未解决的 Issue（方便贡献） - 技术栈与你熟悉的匹配

推荐：expressjs/express、vercel/next.js、facebook/react（选你熟悉的领域的）

28.2 Step 1：克隆和理解

git clone https://github.com/expressjs/express.git
cd express
claude

这是一个大型开源项目。请帮我理解它的架构：

1. 项目整体结构（用树状图展示，只到第 2-3 层）
2. 核心模块和它们的职责
3. 请求处理流程（从接收请求到返回响应）
4. 中间件系统是如何工作的
5. 扩展点在哪里

输出控制在 50 行以内，重点关注我需要理解的"骨架"。

28.3 Step 3：找一个 Issue

查看这个项目的 open issues。
找一个标记为 "good first issue" 或 "help wanted" 的 issue。
告诉我：
1. Issue 编号和标题
2. 问题描述
3. 涉及哪些文件
4. 难度评估（简单/中等/困难）

28.4 Step 4：Plan Mode 制定方案

（Ctrl+G 进入 Plan Mode）

针对选定的 issue，制定修复方案：
1. 需要修改哪些文件
2. 每个文件做什么修改
3. 需要添加什么测试
4. 预计影响范围

评估风险：这个修改会破坏现有功能吗？

28.5 Step 5：实现和测试

（Ctrl+G 退出 Plan Mode）

按计划实现修复。
修改完成后：
1. 跑项目现有的测试套件
2. 添加针对这次修复的测试
3. 检查代码风格是否符合项目规范

28.6 Step 6：提交 PR

创建分支并提交：
1. 基于最新的 main 创建分支
2. 分支名格式：fix/issue-编号-简短描述
3. Commit message 引用 Issue 编号
4. PR 描述模板：
   - 问题描述
   - 修复方案
   - 测试方式
   - Closes #issue编号

28.7 经验总结

学到了什么： - 如何快速理解大型代码库 - 如何在 Plan Mode 中安全地制定方案 - 如何遵循开源项目的规范提交 PR - 如何用 Claude Code 加速开源贡献

关键洞察：Claude Code 理解大型代码库的能力，是它区别于"代码补全工具"的核心竞争力。Copilot 只能看到当前文件，Agent 能看到整个项目。

第29章：实战 3 —— 搭建自动化工作台

29.1 项目概述

目标：将 GitHub、Notion、Slack 三个工具通过 MCP 连接到 Claude Code，搭建一个统一的自动化工作台。

29.2 Step 1：MCP 配置

// .mcp.json
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@anthropic-ai/mcp-server-github"],
      "env": { "GITHUB_TOKEN": "REDACTED_TOKENxxx" }
    },
    "notion": {
      "command": "npx",
      "args": ["-y", "@notionhq/notion-mcp-server"],
      "env": { "NOTION_API_KEY": "ntn_xxx" }
    },
    "slack": {
      "command": "npx",
      "args": ["-y", "@anthropic-ai/mcp-server-slack"],
      "env": { "SLACK_BOT_TOKEN": "xoxb-xxx" }
    }
  }
}

29.3 Step 2：创建工作流 Skill

帮我创建一个 Skill "daily-standup"：
1. 从 GitHub 读取我昨天和今天的 commit
2. 从 Notion 读取我的任务列表和进度
3. 整合成一份站会报告
4. 输出格式：
   - 昨天完成了什么
   - 今天计划做什么
   - 有没有阻塞项

29.4 Step 3：工作流编排

让 Claude Code 自动完成以下工作流：

1. 每天早上 9 点（用 cron）：
   - 拉取 GitHub 的 open issues
   - 对比 Notion 的任务列表
   - 在 Slack 发送每日工作建议

2. 每次 PR 创建时（用 CI/CD）：
   - 自动审查代码
   - 在 Slack 通知团队
   - 在 Notion 更新任务状态

29.5 Step 4：验证

测试完整工作流：
1. 创建一个测试 Issue
2. 在 Notion 创建对应任务
3. 运行 daily-standup Skill
4. 确认 Slack 收到通知
5. 确认 Notion 任务状态更新

29.6 关键收获

收获 说明
MCP 是连接器 一个配置文件，连接无限工具
Skill 是粘合剂 把多个 MCP 工具组合成一个工作流
Claude Code 是编排器 用自然语言描述工作流，自动执行
数据在工具间流动 GitHub → Claude → Notion → Slack

第30章：实战 4 —— 团队协作最佳实践

30.1 共享 CLAUDE.md

团队中最重要的 Claude Code 资源就是 CLAUDE.md。确保团队所有人共享同一份：

# CLAUDE.md 放在仓库根目录，提交到 Git
git add CLAUDE.md
git commit -m "docs: 添加团队共享的 CLAUDE.md"

团队 CLAUDE.md 应包含： - 项目技术栈和架构 - 代码风格规范（强制） - Git commit 规范 - 测试要求 - 安全红线（"禁止硬编码密钥"） - API 设计规范

30.2 共享 Skills

将团队常用的 Skills 提交到仓库：

.claude/
├── settings.json          # Hooks 配置（团队共享）
├── agents/                # 自定义 Subagents
│   ├── code-reviewer.md
│   └── api-designer.md
└── skills/                # 团队 Skills
    ├── pr-review/
    ├── daily-standup/
    └── deploy-check/

团队 Skills 规范： - 每个 Skill 有清晰的触发条件 - 包含完整的步骤说明 - 有输出格式规范 - 定期维护更新

30.3 Hooks 团队配置

在 .claude/settings.json 中配置团队级的 Hooks：

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "command": "阻止 rm -rf / 和 DROP TABLE 等危险命令"
      }
    ],
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "command": "修改 .ts/.js 文件后自动运行 eslint --fix"
      }
    ]
  }
}

30.4 代码审查自动化

CI/CD 中的 Claude Code：

# .github/workflows/claude-review.yml
# 每次 PR 自动触发 Claude 代码审查
# 审查结果作为 PR 评论发布
# 严重问题自动打上 "needs-review" 标签

结合 GitHub CODEOWNERS： - 关键文件的变更自动触发更严格的审查 - Claude Code 负责第一轮审查，人类做最终确认

30.5 知识沉淀

定期更新 CLAUDE.md： - 每季度审查一次 - 新增的技术栈和规范及时更新 - 删除过时的约束 - 收集团队反馈，持续改进

创建团队知识库：

docs/
├── architecture/          # 架构文档
├── decisions/             # ADR（架构决策记录）
├── runbooks/              # 运维手册

让 Claude Code 在 docs/ 中生成和维护文档：

保持与代码同步。

附录 D：常见问题 FAQ

安装与配置

Q：安装后 claude 命令找不到？ A：npm 全局路径未加入 PATH。运行 npm config get prefix，将输出的 bin 目录加入 PATH。

Q：Node.js 版本不满足要求？ A：使用 nvm 安装最新 LTS：nvm install --lts。

Q：登录一直超时？ A：检查网络代理。或使用 API Key 方式：export ANTHROPIC_API_KEY=sk-ant-xxx。

使用问题

Q：Claude 改了不该改的文件怎么办？ A：git checkout -- <file> 恢复。建议在操作前先创建分支，方便回滚。

Q：对话太长，Claude 开始"健忘"？ A：运行 /compact 压缩上下文，或开新会话。超过 75% 上下文使用率就该注意了。

Q：Claude 写的代码有 bug？ A：正常。用四步恢复法：识别→定位→修复→验证。永远不要跳过审查。

Q：Plan Mode 和普通模式有什么区别？ A：Plan Mode 只读不写，适合理解和规划。普通模式可以修改文件。

成本问题

Q：一个月大概花多少钱？ A：轻度使用 $20 内，中度 $20-50，重度 $50-100。设置 Anthropic Console 的月度限额。

Q：如何降低成本？ A：用 /compact、用 Subagent 隔离长任务、日常任务用便宜模型、定期开新会话。

团队问题

Q：团队如何共享 Claude Code 配置？ A：将 CLAUDE.md、.claude/ 目录提交到 Git 仓库。所有成员共享同一套规范。

Q：Claude Code 能替代代码审查吗？ A：不能。Claude 做第一轮审查（速度快），人类做最终确认（质量高）。两者结合效率最高。

全书完

本指南基于 2026 年 5 月公开资料及实际使用经验整理。Claude Code 更新频繁，建议关注官方文档获取最新特性。

记住：工具会变，但方法论不变。四阶段工作流、验证思维、上下文管理——这些原则无论 Claude Code 怎么更新都适用。
