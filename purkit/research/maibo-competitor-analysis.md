## 一、逐项拆解

### 1️⃣ 项目总结汇报

**这是什么**：NPI 项目从立项到量产（或阶段性完成）后，自动汇总项目数据，生成结构化的项目总结报告。

**ODM 场景中的痛点**：
- PM 每个项目结束要花 1-2 天整理 PPT，从 ERP/PLM/MES 多个系统拉数据
- 汇报格式不统一，有的项目详有的略
- 跨部门信息分散（采购有采购的数据、品质有品质的、工程有工程的）
- 管理层要的是"一页纸结论"，PM 给的是 50 页流水账

**AI 做了什么**：
- 连接 ERP/PLM/MES/邮件系统，自动抓取项目全周期数据
- 按 WBS 结构自动归集：进度达成率、成本偏差、质量指标、供应商表现
- 用大模型生成结构化总结（背景→目标→成果→问题→经验）
- 支持一键导出 PPT/Word

**技术难度**：⭐⭐（低）
- 本质是 RAG + 结构化报告生成
- 模板化程度高，格式固定
- 关键壁垒在数据打通（API 对接 ERP/PLM），不在 AI

**scm-skill 覆盖度**：
| Skill | 能力 | 覆盖 |
|-------|------|------|
| m1@project-management D1-D10 | 全生命周期维度 | ✅ 报告框架已定义 |
| p8@cost-execution | 成本偏差分析 | ✅ |
| p4@delivery-track | 交付达成率 | ✅ |
| p9@quality-execution | 质量指标 | ✅ |

**结论**：scm-skill **框架已有**，缺的是数据对接层（API 接入 ERP/PLM）。做成 Skill 的话，输入项目数据 → 自动输出报告模板，1-2 天可完成。

### 2️⃣ 项目进度

**这是什么**：实时追踪 NPI 项目各阶段（EVT→DVT→PVT→MP）的里程碑进度，自动识别延期风险。

**ODM 场景中的痛点**：
- 依赖甘特图/Excel 手动更新，信息滞后
- 关键路径上的长周期物料（芯片、定制件）经常被忽略，直到缺料才发现
- 跨部门依赖关系不清晰（"等工程确认后才能下单"——工程什么时候确认？）
- 风险预警靠人工，往往事后才知道

**AI 做了什么**：
- 自动同步各系统数据（ERP 订单状态、PLM 设计阶段、MES 产线进度）
- 关键路径自动计算 + 动态更新
- 延期风险提前预警（"XX物料预计延期 5 天，影响 DVT 节点"）
- 自然语言查询（"XX 项目现在卡在哪？"）

**技术难度**：⭐⭐⭐（中）
- 需要对接多个数据源（ERP/PLM/MES/供应商协同平台）
- 关键路径计算是确定性算法（CPM），AI 负责的是"解读+预警"
- 关键壁垒在数据打通和实时性

**scm-skill 覆盖度**：
| Skill | 能力 | 覆盖 |
|-------|------|------|
| m1@project-management D4 | 关键路径法、长周期物料识别 | ✅ 框架有，缺系统对接 |
| m1@project-management D7 | 风险预警 | ✅ 7类风险清单 |
| p4@delivery-track | 交付跟踪 | ✅ 催/增/替/调/谈/防 |
| p3@demand-analyze | 需求追踪 | ✅ |

**结论**：scm-skill 的 D4 进度管理框架已经很完善（关键路径法、长周期物料提前识别、进度压缩策略）。缺的是**数据层**——自动从 ERP 拉取实际进度 vs 计划进度的对比。做成 Skill 的话，可以做到"输入进度数据 → 输出关键路径分析 + 风险预警"。

---

### 3️⃣ 试产策略规划、复制模互配计划

**这是最专业的一个，也是最有技术含量的。**

#### 3a. 试产策略规划

**这是什么**：NPI 项目从设计验证到量产之间，AI 帮助规划试产（PVT）的整体策略——试产几次？每次多少数量？验证什么？风险在哪？

**ODM 场景中的痛点**：
- 试产次数太多 → 成本高、周期长
- 试产次数太少 → 量产后问题爆发
- 没有结构化的试产规划方法，全靠经验
- 工程变更（ECN）和试产计划脱节，导致"试了白试"

**AI 做了什么**：
- 基于产品复杂度、供应链成熟度、历史数据，推荐试产策略
- 自动生成试产计划（数量、时间、验证项、通过标准）
- 识别高风险试产项（新物料、新工艺、新供应商的组合）
- 与 ECN 变更联动，确保"改完再试"

#### 3b. 复制模互配计划

**"复制模"**：ODM 场景下，一个产品平台通常会衍生多个型号/配置，需要在不同的模具/产线上"复制"生产。"复制模互配"是指：当同一个产品的不同型号使用不同模具或不同供应商时，如何确保它们之间的零部件能够互换、互配。

**具体场景**：
- A 客户定制版用模具 M1，B 客户定制版用模具 M2
- M1 和 M2 生产的同一个零件，尺寸公差是否一致？
- 换供应商后，新供应商的零件能否与原有模具/零件互配？
- 多工厂生产同一产品时，不同工厂的 BOM 如何管理互配关系？

**AI 做了什么**：
- 自动分析多版本 BOM 之间的差异（哪些料相同、哪些不同、公差要求是否一致）
- 生成互配验证计划（哪些组合需要做交叉验证）
- 识别互配风险（"A 版本用 0402 封装，B 版本用 0201 封装，PCB 焊盘不兼容"）
- 与 BOM 版本管理系统联动

**技术难度**：⭐⭐⭐⭐（高）
- "复制模互配"是一个极其垂直的 ODM 专业场景，需要深入理解模具工程、公差分析、PCB 设计
- 需要对接 PLM/BOM 系统，进行多版本 BOM 差异比对
- 试产策略需要历史数据积累（什么复杂度的产品一般需要几次试产）

**scm-skill 覆盖度**：
| Skill | 能力 | 覆盖 |
|-------|------|------|
| m1@project-management D6 | 质量分阶段门控 | ⚠️ 部分覆盖 |
| p9@quality-execution | 验证标准、AQL | ⚠️ 部分覆盖 |
| p2@p2p-analyze | 替代料评估 | ⚠️ 可借鉴框架，但场景不同 |
| p3@demand-analyze | 需求规格管理 | ⚠️ 部分覆盖 |

**结论**：这是五个应用中 scm-skill 覆盖度最弱的。"复制模互配"是一个 ODM 特有的专业场景，我们的 Skill 目前没有专门覆盖。但这恰恰也是一个差异化机会——如果我们在 scm-skill 中新增一个 `m1b@trial-production` 或 `p10@tooling-management` Skill，专门覆盖试产策略 + 模具互配，就能补上这个缺口。

**但老实说**：这个功能的技术壁垒不在 AI 模型能力，而在**行业Know-How的编码化**。复制模互配的规则是什么？公差匹配的标准是什么？这些需要你的实战经验来定义。

### 4️⃣ BOM 创建

**这是什么**：基于产品需求/设计文档，AI 自动生成或辅助创建 BOM（物料清单）。

**ODM 场景中的痛点**：
- 工程出设计图纸后，需要人工逐行录入 BOM → 耗时长、容易漏项
- 标准件（电阻、电容、螺丝）的选型需要查规格书 → 繁琐
- BOM 层级关系（整机→组件→零件）需要手动维护
- EBOM（工程BOM）到 MBOM（制造BOM）的转换需要大量人工

**AI 做了什么**：
- 从设计文档/原理图/Gerber 文件中自动提取物料信息
- 自动匹配标准件库（"这个 10μF 0402 电容 = 料号 XXXXX"）
- 智能推荐替代料（"原厂停产，推荐替代料 YYYYY"）
- EBOM → MBOM 自动转换（加入包装、辅料、工艺件）
- BOM 完整性检查（有没有漏料？层级关系对不对？）

**技术难度**：⭐⭐⭐（中高）
- 从原理图/Gerber 提取信息需要专用解析器（不是纯 AI 能做的）
- 标准件匹配需要物料主数据库
- AI 的核心价值在"智能推荐"和"完整性检查"

**scm-skill 覆盖度**：
| Skill | 能力 | 覆盖 |
|-------|------|------|
| c5@product-analyze | 产品结构拆解 | ✅ 8D×3I 产品分析框架 |
| p2@p2p-analyze | 替代料推荐 | ✅ 8D×3I 替代料评估 |
| p8@cost-execution | BOM 成本拆解 | ✅ |
| p3@demand-analyze | 需求规格管理 | ✅ |

**结论**：BOM 创建分两部分——**数据提取**（需要解析器，不是 AI 的活）和**智能辅助**（AI 能做的）。AI 的价值在于：
1. BOM 完整性检查（"你的 BOM 里缺了螺丝"）
2. 替代料推荐（"这个芯片交期 52 周，建议换 X"）
3. 成本预估（基于 BOM 自动生成 Should-Cost）

scm-skill 的 c5（产品分析）、p2（替代料）、p8（成本执行）已经覆盖了 BOM 创建的大部分"智能辅助"需求。

### 5️⃣ 产品定义应答

**这是最有意思的一个——也是最体现 ODM 商业模式的。**

**这是什么**：品牌方（客户）发出产品需求/规格书，ODM 厂商的 AI 自动解析需求，生成技术方案应答。

**ODM 商业流程**：
```
品牌方发 RFQ（Request for Quotation）
  ↓ 包含：产品功能定义、性能要求、外观需求、预算范围、时间要求
ODM 厂商收到
  ↓ 需要：理解需求 → 评估技术可行性 → 选定平台方案 → 报价 → 交付计划
AI 自动完成"理解需求 + 评估可行性 + 生成方案应答"
```

**ODM 场景中的痛点**：
- 客户的需求描述往往是模糊的（"要一个智能音箱，音质好，成本控制在 200 以内"）
- 从模糊需求到具体方案，需要多个部门协同（硬件、软件、结构、采购）
- 传统流程：销售→PM→工程→采购→报价，周期 1-2 周
- 竞争激烈时，应答速度就是中标率

**AI 做了什么**：
- 自动解析客户需求文档（PRD/RFP/邮件），提取关键参数
- 匹配内部产品平台（"这个需求适合用我们的 XX 平台"）
- 自动评估技术可行性（"蓝牙 5.3 + 双喇叭 + 电池续航 8h = 可行"）
- 自动生成初步 BOM 和成本估算
- 自动生成交付时间线（基于历史项目的 NPI 周期）
- 输出结构化的应答文档（方案概述 + 技术参数 + 报价 + 交付计划）

**技术难度**：⭐⭐⭐⭐（高）
- 需求解析 → 自然语言理解 + 结构化提取 ✅ AI 擅长
- 平台匹配 → 需要内部产品数据库 ❌ 需要数据
- 技术可行性评估 → 需要工程知识库 ⚠️ 半 AI 半知识库
- BOM + 成本估算 → RAG + 成本模型 ⚠️ 需要 scm-skill 支持
- 交付时间线 → 基于历史数据的预测 ⚠️ 需要数据

**scm-skill 覆盖度**：
| Skill | 能力 | 覆盖 |
|-------|------|------|
| c5@product-analyze | 产品需求解析 | ✅ 产品 8D 分析 |
| c3@company-research | 客户分析 | ✅ 客户画像 |
| p8@cost-execution + c6@cost-analyze | 成本估算 | ✅ Should-Cost |
| m1@project-management | 交付计划 | ✅ NPI 周期估算 |
| p1@supplier-analyze | 供应商匹配 | ✅ 寻源评估 |

**结论**：产品定义应答是一个**复合场景**，需要调用 scm-skill 的多个 Skill 协同工作。恰好符合我们的 CMP 知·管·行架构：
- CEA（知）：c5 分析客户需求 + c6 评估成本可行性
- MGT（管）：m1 规划项目交付 + m3 评估供应商
- PUR（行）：p1 匹配供应商 + p8 生成成本估算

**这是 scm-skill 最能大放异彩的场景。** 因为它本质上就是 scm-skill "知·管·行"双轨架构的自动化编排——从理解需求（知）到规划方案（管）到生成报价（行），一条龙。

## 三、核心洞察

### 3.1 麦博做的是什么

从五个应用的组合来看，麦博本质上是一个 **"ODM NPI 全流程 AI Copilot"**：

```
客户需求 → [产品定义应答] → 方案确定
    ↓
项目启动 → [项目进度] → 全程追踪
    ↓
设计完成 → [BOM创建] → 物料清单
    ↓
试产准备 → [试产策略/复制模互配] → 试产计划
    ↓
项目结束 → [项目总结汇报] → 复盘归档
```

这五个功能串起来，覆盖了 ODM NPI 的**完整生命周期**。这不是五个独立工具，而是一个**流程智能体平台**。

### 3.2 我们 vs 麦博 的本质差异

| 维度 | 麦博（推测） | 我们的 scm-skill |
|------|------------|-----------------|
| **定位** | NPI 项目管理工具 + AI | 采购知识体系 + AI |
| **覆盖范围** | NPI 全流程（研发→采购→制造） | 采购全生命周期（认知→管理→执行） |
| **深度** | 中等（项目管理 + BOM + 试产） | 深（21个Skill，8770字框架） |
| **广度** | 窄（聚焦 NPI 项目管理） | 宽（采购全场景） |
| **技术壁垒** | 数据对接 + 系统集成 | 知识框架 + 行业经验 |
| **可复制性** | 低（依赖企业内部数据） | 高（框架通用） |

### 3.3 关键判断

**麦博强在"数据打通"，我们强在"知识深度"。**

- 麦博的五个功能，技术核心不是 AI 模型能力，而是**企业内部数据系统的 API 对接**。没有 ERP/PLM/MES 的数据，这些功能都是空壳。
- 我们的 scm-skill，核心壁垒是**采购知识框架的深度和结构化程度**。不需要对接任何外部系统，AI 本身就能提供价值。
- **两者的交集在"产品定义应答"**——这是最需要 AI 推理能力、最不依赖数据对接、最匹配我们 scm-skill 架构的场景。

## 四、行动建议

### 方案 A：补短板（对标麦博）

在 scm-skill 中新增 ODM NPI 专属 Skill：
- `m1b@trial-production`（试产策略规划）
- `p10@tooling-management`（复制模互配管理）
- `p11@bom-assistant`（BOM 智能辅助创建）

**代价**：这 3 个 Skill 需要你大量输入 ODM 试产/模具的实战经验，开发周期 2-4 周。

### 方案 B：扬长板（差异化）

不做 NPI 项目管理工具（那是麦博的赛道），而是聚焦我们的优势——**采购决策智能**：
1. **产品定义应答**是我们的天然场景，多 Skill 编排即可实现
2. **项目总结汇报**和**BOM创建**作为轻量工具快速推出
3. 试产策略/复制模互配留给专业 PLM 系统去做

### 方案 C：融合（最佳路径）

```
短期（1-2周）：
  ✅ 做一个"产品定义应答" Skill（多 Skill 编排）
  ✅ 做一个"项目总结汇报" Skill（模板 + m1 框架）
  ✅ 做一个"BOM 智能检查" Skill（完整性检查 + 替代料推荐）

中期（1-2月）：
  ⚠️ 收集试产/模具的实战经验，逐步补全试产策略 Skill
  ⚠️ 与 ERP/PLM 系统的 API 对接（如果公司有需求）

长期（3-6月）：
  🔮 建成 ODM NPI + 采购决策的完整 AI 平台
  🔮 比麦博多出来的差异化：谈判训练(PurKit) + 成本穿透 + 供应商管理
```

## 五、一句话结论

> **麦博做的是 NPI 的"项目管理自动化"，我们做的是采购的"认知与决策智能化"。两者有交集但不冲突——我们的 scm-skill 框架深度是麦博没有的壁垒，而"产品定义应答"这个复合场景恰好是我们最擅长、最能大放异彩的切入点。**
