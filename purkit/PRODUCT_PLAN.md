# PurKit 产品规划 v1.0

> **一句话定位**：采购飞行模拟器——让采购员在安全环境中犯完所有该犯的错。
>
> **灵感来源**：MedKit（Anthropic Opus 4.7 黑客松金奖）——"让医学生在上岗前先犯完所有的错"
>
> **内核来源**：scm-skill CMP 架构（知·管·行）21 个 Skill，8770+ 字采购知识框架

---

## 一、产品哲学

### 1.1 为什么 PurKit 而不是"采购培训课"

传统采购培训有三个致命缺陷：

| 缺陷 | 传统培训 | PurKit |
|------|---------|--------|
| **被动吸收** | 听讲座、看PPT、背框架 | 主动决策，在对话中犯错和纠错 |
| **脱离情境** | 案例是"别人的故事" | 你是当事人，供应商在跟你对线 |
| **没有反馈** | 学完不知道自己掌握到什么程度 | 每轮结束即时评分 + 逐项改进建议 |

PurKit 的底层逻辑与 MedKit 相同：**经验不可传授，只能习得。** 你可以读一百本谈判书，但第一次面对强势供应商要求涨价 15% 时，你还是会慌。PurKit 让你提前慌完。

### 1.2 与 scm-skill 的关系

```
scm-skill = AI 的操作手册（让 AI 变成采购专家）
PurKit   = 人的训练场（让人变成采购专家）
```

两者共享同一个知识内核（CMP架构），但产品形态和用户完全不同：

| 维度 | scm-skill | PurKit |
|------|-----------|--------|
| 用户 | AI Agent | 人 |
| 方向 | 人→AI（指令） | AI→人（挑战） |
| 输出 | 分析报告 | 评分 + 改进建议 |
| 形态 | SKILL.md | Web App |

**scm-skill 是 PurKit 的评分引擎，PurKit 是 scm-skill 的变现通道。**

### 2.3 Layer 2 · 交互层（核心体验）

#### 对话模式

PurKit 有两种交互角色：

**角色 A · 对手（Opponent）**
- AI 扮演供应商（销售/老板/法务）
- 根据剧本设定有性格、底线、隐藏信息
- 目标：让采购员的任务尽可能难完成

**角色 B · 教练（Coach）**
- 谈判结束后介入评分
- 逐维度打分，引用 scm-skill 框架
- 给出具体改进建议（不是泛泛而谈，而是"你的 D1 情报准备不足，没有查供应商产能利用率"）

#### 交互流程

```
选择场景 → 阅读背景 → 开始对话（对手角色）
    ↓
多轮对话（采购员 vs AI供应商）
    ↓
对话结束（双方达成协议 / 谈判破裂 / 时间耗尽）
    ↓
教练评分（按 scm-skill 框架逐维度打分）
    ↓
复盘报告（得分 + 失分点 + 改进建议 + 参考答案）
    ↓
重新挑战 or 下一关
```

#### 评分维度设计原则

1. **不是判断"对错"，而是判断"优劣"**——采购没有标准答案
2. **评分维度 = scm-skill 框架维度**——用同样的语言体系
3. **每个评分项有明确的"达标标准"**——避免主观模糊
4. **分数之外更重视"改进建议"**——知道错在哪比知道得了多少分更重要

### 2.4 Layer 3 · 学习层（长期价值）

#### 能力模型

基于 scm-skill 的 CMP 三层架构，定义采购员能力模型：

```
                    ┌─────────────────┐
                    │   L5 采购总监    │  综合战役 + 团队管理
                    │   全链路联动决策  │
                    ├─────────────────┤
                    │   L4 资深采购    │  战略采购 + 品类管理
                    │   成本穿透 + 金融  │
                    ├─────────────────┤
                    │   L3 高级采购    │  复杂谈判 + 合同博弈
                    │   替代料 + 品质风控 │
                    ├─────────────────┤
                    │   L2 中级采购    │  基础谈判 + 供应商管理
                    │   交付跟踪 + 需求管理│
                    ├─────────────────┤
                    │   L1 初级采购    │  寻源评估 + 报价分析
                    │   基本沟通 + 流程合规│
                    └─────────────────┘
```

#### 学习路径

| 级别 | 解锁场景 | 对应 Skill | 场景数 |
|------|---------|-----------|--------|
| L1 入门 | 供应商评估、需求管理、报价分析 | p1, p3, c6(轻量) | 3-4 |
| L2 进阶 | 基础谈判、交付跟踪、供应商管理 | p5(D1-D3), p4, m3(S01-S04) | 4-5 |
| L3 高级 | 涨价应对、年度降价、合同博弈、品质索赔 | p5(全), p6, p8, p9 | 5-6 |
| L4 专家 | 替代料评估、成本拆解、战略供应商退出 | p2, p8(深度), c2, m3(S08) | 4-5 |
| L5 总监 | 综合战役（多场景联动）、供应链金融 | m4, m5, 全链路联动 | 3-4 |

#### 进度追踪

- 每个场景首次通关、最佳成绩、尝试次数
- 能力雷达图（谈判力/分析力/风控力/成本力/合规力）
- 学习曲线追踪（得分随练习次数的变化趋势）

## 三、场景剧本设计规范

### 3.1 剧本六要素

每个场景剧本必须包含：

```
1. 背景设定    → 采购员看到的情境（邮件/电话/会议通知）
2. 供应商后台  → 评分者看到的信息（真实动机、底线、隐藏信息）
3. 评分标准    → 基于 scm-skill 对应 Skill 的维度分解
4. 供应商行为  → AI 扮演对手时的性格、话术、让步路径
5. 满分示范    → 高分解答示例（不是唯一正确答案）
6. 版本信息    → 创建日期、基于哪个 Skill、难度等级
```

### 3.2 剧本设计原则

| 原则 | 说明 | 反例 |
|------|------|------|
| **真实感** | 每个剧本必须基于真实采购经历 | 脱离实际的"理想化"案例 |
| **信息不对称** | 供应商有隐藏信息，采购员需要自己挖 | 所有信息一开始就透明 |
| **多解性** | 没有"唯一正确答案"，但有优劣之分 | 强制走唯一路径 |
| **递进难度** | 同一场景可以有简单/中等/困难模式 | 只有单一难度 |
| **知识嵌入** | 剧本中嵌入行业知识和实操技巧 | 纯粹考验口才 |

## 四、技术方案

### 4.1 MVP 技术栈（最简方案）

```
Frontend:  Next.js + Tailwind CSS（聊天UI）
Backend:   Node.js + Express（API Server）
AI:        Claude API（对手 + 教练两个角色）
Data:      Markdown files（场景剧本存储）
Deploy:    Vercel（前端） + Railway/Fly.io（后端）
```

**为什么选这个方案：**
- 一个人能搞定，不需要后端数据库
- 场景剧本用 Markdown，方便你直接编写和版本管理
- Claude API 的角色扮演能力最强（MedKit 用的就是 Claude）
- 可以快速迭代，不需要 DevOps

### 4.2 进阶方案

```
Frontend:  Next.js + Three.js（可选3D场景，如会议室/工厂）
Backend:   Python FastAPI + LangGraph（多Agent编排）
AI:        Claude Haiku（对手，快且便宜）+ Claude Opus（教练，精准评分）
Voice:     LiveKit + Deepgram + Cartesia（可选语音模块）
Auth:      NextAuth.js + Stripe（订阅付费）
Data:      PostgreSQL + Prisma（用户数据、成绩、进度）
Deploy:    Vercel（前端） + AWS/GCP（后端）
```

### 4.3 AI 模型选择

| 角色 | 推荐模型 | 原因 | 成本估算 |
|------|---------|------|---------|
| 对手（Opponent） | Claude Haiku 4.5 | 角色扮演不需要太强推理，快且便宜 | ~$0.01/轮 |
| 教练（Coach） | Claude Sonnet 4 | 需要准确按框架评分，推理能力要强 | ~$0.05/次 |
| 剧本生成 | Claude Opus 4 | 从真实经验生成高质量剧本 | ~$1/个剧本 |

**单次场景成本估算**：对话 5-10 轮 × $0.01 + 评分 $0.05 ≈ **$0.15/次**

- 用户分享自己的"谈判翻车"故事，筛选有价值的改编成剧本
- UGC 案例库 = 免费的内容 + 用户粘性

**阶段三（6-12 月）：ToB 企业版**
- 企业培训预算是 Pro 版的 100 倍
- 与 CIPS/ISM 认证体系挂钩
- 目标：签 3-5 家标杆企业客户

## 六、开发路线图

### Phase 0 · 验证（第 1-2 周）

**目标**：验证"采购人觉得这个东西有用"

| 任务 | 交付物 | 负责人 |
|------|--------|--------|
| 写完 MVP 6 个场景剧本 | 6 个 Markdown 文件 | Ken（经验输入）+ AI（结构化） |
| 在 Claude 里手动跑 3 个场景 | 3 段对话记录 | AI |
| 发给 5-10 个采购圈朋友测试 | 反馈收集 | Ken |
| 回答关键问题："你愿意为这个付 99 元/月吗？" | Go/No-Go 决策 | Ken |

**里程碑**：如果 >60% 的人说"愿意"，进入 Phase 1

### Phase 1 · MVP（第 3-5 周）

**目标**：可用产品上线，收集真实用户数据

| 任务 | 交付物 | 技术方案 |
|------|--------|---------|
| 聊天 UI | Web App | Next.js + Tailwind |
| 对话引擎 | API | Claude API |
| 评分系统 | 评分报告 | 基于剧本的 rubric |
| 3 个场景上线 | 可用产品 | Markdown 剧本 |
| 用户注册/登录 | Auth | NextAuth |
| 部署上线 | 生产环境 | Vercel |

**里程碑**：50 个注册用户，平均完成 2+ 个场景

### Phase 2 · 扩展（第 6-10 周）

**目标**：6 个场景全部上线，加入学习路径

| 任务 | 交付物 |

## 七、关键风险与应对

| 风险 | 概率 | 影响 | 应对策略 |
|------|------|------|---------|
| **案例质量不够真实** | 中 | 致命 | 你亲自写，从真实经历中提取；找 3-5 个资深采购审稿 |
| **采购人不习惯"AI训练"** | 中 | 高 | 用内容教育市场；从"面试准备"切入（刚需） |
| **评分标准太主观** | 高 | 中 | 评分维度来自 scm-skill 成熟框架；持续校准 |
| **被抄袭** | 高 | 低 | 案例库是壁垒；快速迭代；先发优势 |
| **AI成本过高** | 中 | 中 | 对手用 Haiku（便宜），教练用 Sonnet（够用）；单次成本 ¥1 以内 |
| **市场太小** | 低 | 高 | 全球采购从业者数千万；中国企业培训市场巨大 |

## 八、与 scm-skill 的协同演进

```
Phase 0-1: PurKit 依赖 scm-skill（单向）
    scm-skill 框架 → PurKit 评分标准
    scm-skill 知识 → 场景剧本背景

Phase 2-3: 双向反馈（飞轮启动）
    PurKit 用户对话数据 → 优化评分维度
    PurKit 高频错误 → 补充 scm-skill 知识盲区
    PurKit UGC 案例 → 反哺 scm-skill 框架迭代

Phase 4: 生态融合
    scm-skill = PurKit 的评分引擎（B2B）
    PurKit = scm-skill 的获客入口（B2C）
    共同构成"采购知识操作系统"
```
