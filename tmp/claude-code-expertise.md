# Agentic Coding and Persistent Returns to Expertise

## 代理式编程与专业技能的持续回报

**Agentic Coding and Persistent Returns to Expertise**

**——Claude Code 在实践中的应用研究**

---

**作者：** Zoe Hitzig, Maxim Massenkoff, Eva Lyubich, Shaoyi Zhang, Ryan Heller, Peter McCrory

**发表日期：** 2026年6月16日

**来源：** Anthropic Research

---

## 核心发现

- 在先前关于自主性衡量和 AI 如何改变 Anthropic 内部工作的研究基础上，我们提出了一种基于隐私保护分析的交互式代理编程研究框架，分析了 2025 年 10 月至 2026 年 4 月间约 **40 万个 Claude Code 会话**。我们评估了任务构成、人机协作模式以及成功率。

- 在典型会话中，人类做出大部分**规划决策**（做什么），而 Claude 做出大部分**执行决策**（怎么做）。人类带入会话的领域专业知识越多，Claude 在每条指令下完成的工作量就越大。在编程任务中，**所有主要职业的编程成功率几乎与软件工程师持平**——都有可验证的证据表明任务已达成，如测试通过或代码已提交。

- 人类在会话中展现的领域专业知识越多，会话成功的概率就越高——不过中级用户与专家用户之间的差距并不显著。在我们观察的七个月里，用于调试的会话比例下降了近一半，使用场景转向了更多端到端的代理化应用：部署和运行代码、分析数据、编写非代码文档。

- 在这七个月间，典型任务的估值——通过对比自由职业招聘帖子来估算——在几乎所有类型的工作中都有所上升，平均约 **25%**。

## 引言

代理式编程已经起飞。GitHub 上有编程代理活动的项目份额自 2025 年底以来增长了一倍以上¹，Claude Code 用户现在平均每周使用该工具 **20 小时**²。没有正式编程经验的人能否成功指挥代理完成复杂的技术工作？这些工具的快速采用和改进对知识工作者来说意味着什么？

虽然我们还没有完全回答这些问题，但我们从 Claude Code 使用数据中寻找早期信号。

本报告基于 2025 年 10 月至 2026 年 4 月间约 **23.5 万人** 的约 **40 万个交互式会话** 的隐私保护分析，提供关于 Claude Code 实际使用方式的证据。它建立在先前关于 Claude Code 会话自主性衡量指标以及 Claude Code 如何改变 Anthropic 内部工作的研究基础上³。在此，我们引入一个描述交互式 AI 编程助手使用方式的框架：正在做什么类型的工作，谁在做，以及是否成功。

随着模型变得更有能力，通过追踪代理式编程使用方式的变化，我们可以更好地理解这些工具如何影响编程专业人员和知识工作者的劳动力市场。

Claude Code 上发生的事情可能是知识工作走向何方的一个预览，因为代理正在嵌入到非编程工作中。我们发现 Claude 正在处理更复杂、更有价值的任务。与此同时，代理式编程中仍存在明确的劳动分工：**人决定构建什么，代理决定如何构建**。

我们还看到证据表明，**领域专业知识而非编程能力**才是放大工具有效使用的关键。特别是，领域专家成功的次数更多，更容易从错误和误解中恢复。然而，专家与中级用户之间的差距是适度的——这表明在一个领域的胜任能力足以几乎和深度精通者一样有效地使用该工具。

这些发现为我们提供了劳动力市场可能转变的早期判断。在我们的数据中，成功取决于一个人对其试图解决的问题的理解程度，而非其是否受过编程训练。如果这些模式在整个经济中成立，则表明虽然代理式编程工具可能正在吸收一些实施量大的工作，但它们也在奖励那些对工作中所解决问题有扎实理解的人。**编程代理并没有替代领域专业知识——工作者带给代理的理解越多，代理能产出的高质量工作就越多。**

## 劳动分工

### 人们用 Claude Code 做什么

为了理解人们用 Claude Code 做什么，我们将每个会话分类到九种工作模式之一——最能描述该会话试图完成的活动。

四种模式涉及直接编写或维护代码：**构建新事物**、**修复损坏的事物**、**测试代码**、**编排其他代理或自动化流水线**。另一个类别是**操作软件**——部署、配置、运行流水线、监控系统。两个类别更偏向于确定做什么：**理解现有系统如何工作**，以及**在做出更改之前规划变更**。还有两个采取与代码无关的行动，或代码对最终产品是次要的：**分析数据**，以及**通过演示文稿和其他基于文本的文档进行沟通**。

约 56% 的会话由编写（25%）、修复（26%）或测试和编排代码（5%）组成。操作软件占 17%，14% 的会话用于规划或探索，13% 产出分析或文本内容。

### 谁决定做什么

Claude Code 有多自主？能力评估表明上限很高且在持续上升：在 METR 的时间跨度评估等基准测试中，前沿模型现在可以自主完成需要人类数小时才能完成的软件任务，并在过程中自主克服障碍。但实际使用中的情况是什么样的？

我们通过两个角度来研究这个问题。首先，我们关注人们将决策委托给 Claude 的程度，其次我们查看他们给 Claude 多少行动指令。

**平均而言，人类做出约 70% 的规划决策，但仅做出 20% 的执行决策。** 在实践中，代理式编程中存在明确的劳动分工——**人决定构建什么，代理决定如何构建**。

为了理解会话中行动的委托方式，我们查看会话的结构而非内容。一个 Claude Code 会话涉及 Claude 和用户来回交流——用户写一条指令，Claude 去做一些工作，然后用户再写一条指令，如此往复。在典型会话中，大约有四轮这样的交互。在我们的历史数据中（10 月至 4 月），用户发送的每条指令平均会触发 Claude 执行约 10 个操作——有时超过 100 个⁶。在每一轮中，Claude 读取文件、编辑代码、运行命令，平均输出 2,400 字。

### 专业水平

Claude 使用五级评分量表（从新手到专家）评估用户在该任务上表现出的专业水平。专业水平分类器寻找三个信号：用户如何精确地描述其指令、他们要求 Claude 验证什么，以及用户倾向于纠正 Claude 还是 Claude 倾向于纠正用户。

请注意，专业水平捕捉的是与职位头衔或综合能力截然不同的东西，关键是它是**任务特定的**。一位高级工程师首次询问 Rust 问题时就是 Rust 新手。一位从未使用过 Python 的会计师，如果告诉 Claude 一段 Python 脚本必须执行哪些对账规则，并能在月末结账时捕捉到它处理不当的边缘情况，则在该任务上是专家。

在典型的新手会话中，每条指令触发约 5 个 Claude 操作和大约 600 字的输出，而专家会话触发的操作链长度超过两倍（12 个操作），输出量是其五倍（3,200 字）。这种新手与专家会话之间的差距出现在每种工作和每个任务价值区间中。

## 谁在使用 Claude Code，以及用于什么

### 用户

为了理解谁在做这项工作，我们从会话记录中推断每个用户的职业，并将其映射到美国劳工统计局标准职业分类（SOC）分类法的 23 个主要群体之一。分类器被指示仅依赖以下信号：代理在会话开始时加载的项目上下文、文件名和结构、用户引用的任何工件（如法律文件、临床数据、财务报告、课程等），以及他们使用的词汇⁷。它被明确指示不将编码行为本身作为编程职业的证据。

我们能在约 70% 的会话中推断出职业。其中，计算机和数学职业——涵盖大多数软件相关工作——无疑是最大的群体。其次是商业和金融运营、艺术/设计/媒体、管理，以及生命/物理/社会科学。我们样本中增长最快的非软件职业群体是管理、销售和法律职业。

### 工作

在 2025 年 10 月至 2026 年 4 月间，使用 Claude Code 完成的工作构成发生了显著变化。最明显的变化是，用于修复损坏代码的会话比例从 33% 下降到 19%。取而代之的是，围绕代码的工作比例增加了。操作软件从会话的 14% 增长到 21%。编写和数据分析大致翻倍，从约 10% 增长到会话的 20%。

任务本身也变得更有价值。我们通过询问在自由职业市场上完成这项工作需要多少费用来近似估算每个会话的经济价值，对照真实帖子的公开数据集进行校准。按此衡量，平均会话的估算价值在 10 月至 4 月间增长了 **27%**。这种增长在许多类型的工作中都存在。构建、操作和修复类任务都增长了约三分之一或更多（分别约 43%、34% 和 32%）。

## 成功取决于用户带来了什么

会话的成功与用户在会话中展现的专业水平之间存在明确的模式：**人在会话中展现的专业水平越高，成功的可能性就越大。** 大部分收益集中在专业水平的低端——新手会话与中级会话之间的差距大于中级与专家之间的差距。

关于成功的衡量，我们依赖两种互补的基于记录的衡量方法。第一种，**评判成功**，由一个分类器读取完整记录并判断此人是否成功完成了其设定的目标（选项：成功、部分成功、失败、无明确目标）。然后两个配套分类器评估该判断证据的强度，以确定**已验证成功**。

**已验证成功**需要同时满足：会话被评判为成功，并且至少有一个硬性可验证的成功信号（如匹配工作的 git 提交、测试套件通过、用户明确确认等）。

## 专业水平的回报

### 哪种会话最成功？

在我们的所有成功衡量指标中，人在会话中展现的专业水平越高，会话成功的可能性就越大。

一个被评为新手的会话达到我们最严格的衡量标准——已验证成功——的概率为 **15%**，至少部分成功的概率为 **77%**。被评为中级或以上的会话达到已验证成功的概率为 **28-33%**，部分成功为 **91-92%**。

在每种衡量指标中，大部分收益来自从新手提升到中级；在中级和专家之间，斜率下降。

类似的梯度也出现在遇到挑战的会话中。当失败信号记录到已验证的失败证据时（如错误、测试失败、对同一事情的多次尝试、用户表达不满），我们称会话遇到了麻烦。在遇到麻烦的会话中，达到已验证成功的比例从新手评分会话的 **4%** 上升到专家评分会话的 **15%**。

我们还追踪了专业水平与各种失败衡量指标之间的反向关系。当遇到麻烦的会话被判定为失败且零行代码被写入时，我们称该会话被**放弃**：**19%** 的新手用户会话最终被放弃，而其他所有人的比例为 **5-7%**。换句话说，经验最少的用户在难以获得期望结果时更有可能放弃。专业水平的部分价值似乎体现在**将代理引导到正确方向的能力**上。

### 职业可能不如专业水平重要

软件相关职业的用户约 **30%** 的会话达到已验证成功，而其他职业的用户约 **26%**。在产生代码的会话中，这些数字分别为 **34%** 和 **29%**。在我们较宽松的成功定义下，软件相关职业和其他职业的差距缩小了——两个群体在产生代码的会话中至少部分成功的比例分别为 **89%** 和 **88%**。这 5 个百分点的差距很小，在七个月内既没有扩大也没有缩小，尽管两个群体的成功率都在增加。

在我们数据集中产生代码的前十大职业中，每个职业的成功率与软件工程师的成功率差距都在 **7 个百分点以内**。管理职业在已验证成功方面最高，略高于软件工程职业。他们较高的已验证成功率可能反映了可转移到指导代理的管理技能，但也可能部分反映了我们的衡量方式——验证部分依赖于记录中的明确确认，而管理者可能更倾向于在获得期望结果时进行明确沟通。

## 展望

本报告的结果描绘了一幅新兴图景：代理式编程如何放大某些形式的知识和技能，同时替代另一些形式。

在产生代码的会话中，**所有主要职业的成功率都在软件相关职业的几个百分点范围内**。编程代理似乎正在使编程背景对成功编程的相关性降低。

与此同时，成功的会话更可能展现领域专业知识。被评为专家的会话达到已验证成功的频率是新手会话的**两倍以上**，当会话遇到麻烦时，新手放弃会话的比率是其他所有人的数倍。协作模式为这幅图景增添了更多细节——**领域专家能够指导 Claude 在每条指令下做更多工作**。

因此，引导 Claude 走向成功的能力更多来自**对某个领域的掌控**，而非编写代码的能力。在任何领域拥有这种掌控能力的人现在可能能够完成他们以前无法完成的技术工作。缺乏任何这种专业知识的人从同一工具中获得的收益将少得多。而且收益主要来自**胜任力而非精通**——对工作领域的基本掌握就捕获了大部分收益，而深度专业化只在此基础上增加了少许。

这些发现是初步的。我们无法衡量现实世界的结果（如会话中编写的代码是否真正被使用或随后被废弃），本报告排除的非交互式使用占了活动的很大一部分。随着模型、用户以及它们之间的劳动分工发生变化，本报告描绘的图景也将被更新。

例如，如果专业水平的回报随时间开始下降，这将表明模型正在开始提供用户目前带来的关键判断力，这些工具的收益正在向领域专家之外扩大。如果软件职业以外的用户成功完成的编程会话份额继续增长，这可能表明软件生产正在成为每个领域常规工作的一部分，而非单一职业的产物。这些转变将改变谁从代理式编程中受益以及受益程度，并对劳动力市场中最受重视的内容产生影响。
